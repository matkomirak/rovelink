# Technical Implementation Brief: Rovelink Hardening

Implement the following backend, security, testing, and operational improvements.

## 1. Secure `/api/gate` routes with authentication and authorization

### Problem

The gate routes are currently mounted without authentication:

```ts
app.use("/api/gate", gateRoutes);
```

This exposes Automation GATE data publicly, including VM names, asset IDs, NetBox IDs, provider hints, allowed/blocked decisions, and governance failure reasons.

### Required change

Update `server/routes.ts` so `/api/gate` is protected by authentication:

```ts
app.use("/api/gate", authMiddleware, gateRoutes);
```

Then add role-based access controls inside the gate router where appropriate.

Suggested role policy:

| Endpoint type                         | Minimum role |
| ------------------------------------- | ------------ |
| Read gate evaluations                 | `viewer`     |
| Trigger gate re-evaluation            | `operator`   |
| Modify gate settings/rules            | `admin`      |
| Sync gate results back to NetBox/CMDB | `admin`      |

Example:

```ts
router.post(
  "/evaluate",
  requireRole(["operator", "admin"]),
  async (req, res) => {
    // existing handler
  }
);
```

If `requireRole` currently accepts a different signature, adapt accordingly.

### Acceptance criteria

* Unauthenticated requests to `/api/gate/*` return `401`.
* Authenticated viewers can read gate status/evaluation results.
* Viewers cannot trigger syncs, updates, or re-evaluations.
* Operators can run evaluations.
* Only admins can change gate configuration or sync gate blocks externally.
* Add tests for these cases.

## 2. Enforce tenant isolation consistently with `orgId`

### Problem

The database schema includes `orgId`, and some list methods filter by `orgId`, but several single-object read/update/delete operations only use `id`.

Examples that need review:

```ts
getProject(id)
getProvider(id)
getCmdbAccount(id)
updateProvider(id)
deleteProvider(id)
updateCmdbAccount(id)
deleteCmdbAccount(id)
```

This can allow cross-tenant access if a user guesses or obtains another tenant’s UUID.

### Required change

Every tenant-owned resource must be queried, updated, or deleted using both:

```ts
id
orgId
```

Do not trust `orgId` from the client request body.

The authenticated user’s organization should come from the auth context, for example:

```ts
req.orgId
```

or:

```ts
req.user.orgId
```

depending on the existing implementation.

### Example fix

Before:

```ts
await db
  .select()
  .from(providerAccounts)
  .where(eq(providerAccounts.id, id));
```

After:

```ts
await db
  .select()
  .from(providerAccounts)
  .where(
    and(
      eq(providerAccounts.id, id),
      eq(providerAccounts.orgId, orgId)
    )
  );
```

Before:

```ts
await db
  .delete(providerAccounts)
  .where(eq(providerAccounts.id, id));
```

After:

```ts
await db
  .delete(providerAccounts)
  .where(
    and(
      eq(providerAccounts.id, id),
      eq(providerAccounts.orgId, orgId)
    )
  );
```

### Routes to audit

Audit all routes and storage methods for these resource types:

```text
projects
providerAccounts
cmdbAccounts
pipelines
pipelineRuns
mappingRules
automationInventories
jobTemplates
jobRuns
credentials
reports
notifications
settings
netboxVms
```

Any object tied to an organization must enforce `orgId`.

### Creation rule

When creating tenant-owned resources, ignore `orgId` in the client body.

Bad:

```ts
const data = req.body;
await storage.createProvider(data);
```

Good:

```ts
const data = {
  ...req.body,
  orgId: req.orgId,
};
await storage.createProvider(data);
```

Optionally strip dangerous fields:

```ts
const { orgId, userId, id, ...safeBody } = req.body;

const data = {
  ...safeBody,
  orgId: req.orgId,
};
```

### Acceptance criteria

* A user from organization A cannot read, update, delete, launch, or list organization B’s resources.
* Client-provided `orgId` is ignored during creation.
* All tenant-owned single-object methods require `orgId`.
* Add cross-tenant tests for providers, CMDB accounts, projects, job templates, credentials, and gate data.

## 3. Add role enforcement to mutation and execution routes

### Problem

Some backend routes are protected only by `authMiddleware`, not by role checks. This may allow low-privilege authenticated users to create resources, modify secrets, or launch automation jobs.

Examples to review:

```ts
app.post("/api/projects", authMiddleware, ...)
app.post("/api/credentials", authMiddleware, ...)
app.post("/api/templates/:id/launch", authMiddleware, ...)
```

### Required change

Add role enforcement to all write, delete, execution, and sensitive read operations.

Suggested role model:

| Action                                | Minimum role                                     |
| ------------------------------------- | ------------------------------------------------ |
| Read dashboard/list data              | `viewer`                                         |
| Read non-secret configuration         | `viewer`                                         |
| Create/update projects                | `admin`                                          |
| Delete projects                       | `admin`                                          |
| Create/update/delete providers        | `admin`                                          |
| Create/update/delete CMDB accounts    | `admin`                                          |
| Create/update/delete credentials      | `admin`                                          |
| Create/update/delete job templates    | `admin`                                          |
| Launch jobs                           | `operator`                                       |
| Cancel jobs                           | `operator`                                       |
| Create/update/delete inventories      | `operator` or `admin`                            |
| Generate reports                      | `viewer` or `operator`, depending on sensitivity |
| Change settings                       | `admin`                                          |
| Sync provider/CMDB data               | `operator`                                       |
| Sync gate results back to NetBox/CMDB | `admin`                                          |

### Example route change

Before:

```ts
app.post("/api/templates/:id/launch", authMiddleware, async (req, res) => {
  // launch job
```

After:

```ts
app.post(

  }
);
```

Before:


After:

```ts
app.post(
  "/api/credentials",
  authMiddleware,
  requireRole(["admin"]),
  async (req, res) => {
    // create credential
  }
);
```

### Acceptance criteria

* Viewers cannot create, update, delete, sync, or launch automation.
* Operators can launch jobs and run syncs but cannot manage secrets or global settings.
* Admins can manage configuration and credentials.
* Add role-based tests for important routes.

## 4. Restrict local Ansible playbook execution paths

### Problem

The local Ansible runner launches playbooks using a path from the job template:

```ts
args = ["-i", options.inventoryPath, options.playbookPath];
```

Even though `spawn()` is safer than shell execution, the playbook path itself may be unsafe. A user who can create or modify templates could point Ansible to unexpected files on the host.

### Required change

Only allow project-relative playbook paths from the checked-out project directory.

Do not allow:

```text
absolute paths
../ traversal
symlinks escaping project root
paths outside the project checkout
empty paths
non-YAML files if the app expects YAML playbooks
```

### Recommended helper

Create a helper such as:

```ts
import path from "node:path";
import fs from "node:fs/promises";

export async function resolveSafePlaybookPath(
  projectRoot: string,
  playbookPath: string
): Promise<string> {
  if (!playbookPath || typeof playbookPath !== "string") {
    throw new Error("Playbook path is required");
  }

  if (path.isAbsolute(playbookPath)) {
    throw new Error("Absolute playbook paths are not allowed");
  }

  const normalizedRelative = path.normalize(playbookPath);

  if (
    normalizedRelative.startsWith("..") ||
    normalizedRelative.includes(`..${path.sep}`)
  ) {
    throw new Error("Playbook path cannot escape project directory");
  }

  if (!/\.(ya?ml)$/i.test(normalizedRelative)) {
    throw new Error("Playbook must be a YAML file");
  }

  const projectRealPath = await fs.realpath(projectRoot);
  const candidatePath = path.resolve(projectRealPath, normalizedRelative);
  const candidateRealPath = await fs.realpath(candidatePath);

  const relativeToProject = path.relative(projectRealPath, candidateRealPath);

  if (
    relativeToProject.startsWith("..") ||
    path.isAbsolute(relativeToProject)
  ) {
    throw new Error("Playbook path escapes project directory");
  }

  return candidateRealPath;
}
```

Use this before launching Ansible:

```ts
const safePlaybookPath = await resolveSafePlaybookPath(
  project.checkoutPath,
  template.playbook
);

await localRunner.run({
  inventoryPath,
  playbookPath: safePlaybookPath,
  extraVars,
});
```

### Additional requirements

Also validate inventory paths if they are generated on disk.

The inventory file should be created in a controlled runtime directory, for example:

```text
./runtime/inventories/<orgId>/<runId>/inventory.yml
```

The app should not accept arbitrary inventory paths from the client.

### Acceptance criteria

* Absolute playbook paths are rejected.
* `../` traversal is rejected.
* Symlinks escaping the project root are rejected.
* Only `.yml` or `.yaml` files are allowed.
* Playbooks must exist inside the project checkout.
* Add unit tests for safe and unsafe path examples.

## 5. Fix encrypted CMDB config usage in automation inventory generation

### Problem

One route creates a `NetBoxAdapter` directly from `cmdb.config`:

```ts
const adapter = new NetBoxAdapter(cmdb.config as any);
```

Elsewhere, CMDB config is decrypted first:

```ts
const decryptedConfig = decryptCmdbConfig(cmdb.config as Record<string, any>);
```

If the NetBox token is encrypted, this route may fail or send the encrypted token as the API token.

### Required change

Find the route in:

```text
server/routes/automation-inventories.ts
```

Replace direct usage of encrypted config with decrypted config.

### Expected implementation

```ts
import { decryptCmdbConfig } from "../security/secrets";
```

Then:

```ts
const decryptedConfig = decryptCmdbConfig(
  cmdb.config as Record<string, any>
);

const adapter = new NetBoxAdapter(decryptedConfig as any);
```

Make sure the decrypted config is never logged or returned in API responses.

### Acceptance criteria

* Automation inventory generation works with encrypted NetBox tokens.
* Decrypted tokens are not returned in API responses.
* Decrypted tokens are not logged.
* Add a test using an encrypted CMDB token and verify the adapter receives the decrypted token.

## 7. Add `/api/health` endpoint for Docker healthcheck

### Problem

The Dockerfile healthcheck points to:

```dockerfile
http://localhost:5000/api/health
```

But the server does not appear to define this endpoint.

This can cause the Docker container to be marked unhealthy even when the app is running.

### Required change

Add a lightweight health endpoint.

In the main server route registration file:

```ts
app.get("/api/health", (_req, res) => {
  res.status(200).json({
    ok: true,
    service: "rovelink",
    timestamp: new Date().toISOString()
  });
});
```

This endpoint should not require authentication.

### Optional database health endpoint

Keep `/api/health` lightweight and fast.

If database health is needed, add a separate endpoint:

```text
/api/health/db
```

Example:

```ts
app.get("/api/health/db", async (_req, res) => {
  try {
    await db.execute(sql`select 1`);
    res.status(200).json({
      ok: true,
      database: "ok",
      timestamp: new Date().toISOString()
    });
  } catch {
    res.status(503).json({
      ok: false,
      database: "error",
      timestamp: new Date().toISOString()
    });
  }
});
```

### Acceptance criteria

* `curl http://localhost:5000/api/health` returns HTTP `200`.
* Docker healthcheck passes.
* `/api/health` does not expose secrets, config, database URLs, or environment details.
