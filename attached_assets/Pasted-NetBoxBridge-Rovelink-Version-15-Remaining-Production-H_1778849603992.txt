Task 1 — Implement Central Role Hierarchy
-----------------------------------------

Problem:

The documentation says:

    platform_admin > admin > operator > viewer

But the current requireRole implementation appears to check exact role membership only.

That means a platform_admin may fail routes requiring admin unless platform_admin is explicitly listed.

Required implementation:

Create one shared role helper and use it everywhere.

Recommended file:

    server/auth/roles.ts

Suggested implementation:

    export const ROLE_RANK = {
      viewer: 1,
      operator: 2,
      admin: 3,
      platform_admin: 4,
    } as const;

    export type Role = keyof typeof ROLE_RANK;

    export function hasRoleAtLeast(userRole: string | undefined, requiredRole: Role): boolean {
      if (!userRole) return false;

      const userRank = ROLE_RANK[userRole as Role] ?? 0;
      const requiredRank = ROLE_RANK[requiredRole] ?? 999;

      return userRank >= requiredRank;
    }

    export function hasAnyRoleAtLeast(userRole: string | undefined, requiredRoles: Role[]): boolean {
      if (!requiredRoles.length) return false;

      const minimumRequiredRank = Math.min(
        ...requiredRoles.map((role) => ROLE_RANK[role])
      );

      const userRank = ROLE_RANK[userRole as Role] ?? 0;

      return userRank >= minimumRequiredRank;
    }

Update requireRole to use this hierarchy.

Expected behavior:

- viewer can access viewer routes only.
- operator can access operator and viewer routes.
- admin can access admin, operator, and viewer routes.
- platform_admin can access platform_admin, admin, operator, and viewer routes.

Important:

There should be only one requireRole implementation. Remove or replace duplicate local definitions in route files.

Acceptance criteria:

- platform_admin can access admin routes.
- platform_admin can access operator routes.
- platform_admin can access viewer routes.
- admin cannot access platform_admin-only routes.
- operator cannot access admin routes.
- viewer cannot access operator/admin/platform_admin routes.
- Add or update tests for the hierarchy.
- npm test passes.
- npm run check passes.


Task 2 — Restrict Organization Management to platform_admin
----------------------------------------------------------

Problem:

server/routes/organizations.ts currently allows normal admin users to manage organizations.

For a multi-tenant app, organization list/create/update/delete should be platform_admin only.

Required policy:

    GET    /api/organizations          platform_admin only
    POST   /api/organizations          platform_admin only
    PATCH  /api/organizations/:id      platform_admin only
    DELETE /api/organizations/:id      platform_admin only

Current organization route should be separate:

    GET /api/org/current               authenticated user
    PUT /api/org/current               admin or platform_admin, scoped to own org

Required implementation:

Update organization-management routes to require platform_admin.

Example:

    router.get(
      "/",
      authMiddleware,
      requireRole("platform_admin"),
      async (_req, res) => {
        const orgs = await db.select().from(organizations);
        res.json(orgs);
      }
    );

    router.post(
      "/",
      authMiddleware,
      requireRole("platform_admin"),
      async (req, res) => {
        ...
      }
    );

    router.patch(
      "/:id",
      authMiddleware,
      requireRole("platform_admin"),
      async (req, res) => {
        ...
      }
    );

    router.delete(
      "/:id",
      authMiddleware,
      requireRole("platform_admin"),
      async (req, res) => {
        ...
      }
    );

Add tests:

- platform_admin can list organizations.

- platform_admin can update organizations.
- platform_admin can delete organizations.
- admin can update only their current org through /api/org/current if that route exists.
- admin cannot update another org through /api/org/current.

Acceptance criteria:

Task 3 — Generate Real Gated Inventory for Local Ansible Runs
-------------------------------------------------------------

Problem:

createInventoryForRun() currently writes a placeholder inventory:

    all:
      hosts:
        localhost:
          ansible_connection: local

This is safe, but it does not fulfill the product promise.

The product promise is:

    Automation should run only against CMDB-approved / Automation-GATE-approved assets.

Required implementation:

Update createInventoryForRun() so it generates inventory from gate-approved hosts.

Expected behavior:

1. Identify the automation inventory or source inventory connected to the job template/run.
2. Load the inventory hosts for the current org.
3. Apply Automation GATE rules.
4. Include only allowed hosts.
5. Exclude blocked hosts.
6. Write an Ansible YAML inventory file to:

       runtime/inventories/<orgId>/<runId>/inventory.yml

7. Return the absolute safe path.

Recommended function shape:

    export async function createInventoryForRun(options: {
      orgId: string;
      runId: string;
      templateId: string;
      inventoryId?: string | null;
      limitExpr?: string | null;
    }): Promise<string> {
      ...
    }

Inventory file should include metadata comments:

    # Generated by Rovelink
    # Run ID: <runId>
    # Organization ID: <orgId>
    # Gate policy: enforced
    # Blocked hosts excluded

Example output:

    all:
      hosts:
        vm-001:
          ansible_host: 10.0.0.11
          rovelink_netbox_id: 123
          rovelink_gate_status: allowed
        vm-002:
          ansible_host: 10.0.0.12
          rovelink_netbox_id: 124
          rovelink_gate_status: allowed

Required security behavior:

- Do not include blocked hosts.
- Do not include hosts from another organization.
- Do not accept inventory path from the client.
- Ensure parent directories are created safely.
- Use safe path handling for runtime directory creation.
- Do not write secrets into inventory unless explicitly required and encrypted/handled safely.

If the current schema does not yet link job templates to automation inventories, add one of these:

Option A:

    jobTemplates.inventoryId

Option B:

    jobRuns.inventoryId

Option C:

    derive inventory from the template/project/provider/CMDB relationship

Choose the smallest safe change that fits the existing data model.

Acceptance criteria:

- LocalRunner receives a real generated inventory file, not localhost placeholder.
- Inventory contains only gate-approved hosts.
- Blocked hosts are excluded.
- Hosts from other organizations are excluded.
- Tests cover:
  - allowed hosts are included
  - blocked hosts are excluded
  - cross-org hosts are excluded
  - inventory file is written to runtime/inventories/<orgId>/<runId>/inventory.yml

- npm run check passes.


Task 4 — Keep Local Ansible Demo-Labeled or Implement Real Git Sync
-------------------------------------------------------------------

Problem:

Local Ansible path validation is now safer, but project sync is still demo-only.

Current demo behavior uses hardcoded playbooks such as:

    site.yml
    deploy.yml
    rollback.yml

Local Ansible cannot be considered production-functional until real project checkout exists.

Choose one option.

Option A — Keep demo-only behavior for now.

Required changes:

- UI must clearly say "Demo Sync" or "Simulated Sync".
- Documentation must clearly say repository sync is simulated.
- Local production execution should remain disabled unless project.checkoutPath exists.
- Error message should be explicit:

      Local execution requires a real project checkout. Demo sync does not create checkoutPath.

- Do not claim local Ansible execution is production-ready.

Option B — Implement real Git sync.

Required changes:

- Store repository URL and branch/ref.
- Clone or pull repository into:

      runtime/projects/<orgId>/<projectId>/

- Save project.checkoutPath.
- Discover .yml and .yaml playbooks from the checkout.
- Use spawn with argument arrays for git commands.
- Do not shell-interpolate repository URLs.
- Do not log Git credentials or tokens.
- Use credential store for private repo auth.
- Use resolveSafePlaybookPath(project.checkoutPath, template.playbook) before execution.
- Prevent path traversal and symlink escapes.

Acceptance criteria for Option A:

- UI and docs clearly label sync as demo/simulated.
- Local production execution fails safely without checkoutPath.
- No production-readiness doc claims real Git sync.

Acceptance criteria for Option B:

- Real Git checkout works.
- checkoutPath is tenant-scoped.
- Playbooks are discovered from the checked-out repo.
- LocalRunner can run only playbooks inside checkoutPath.
- Git credentials are not logged.

Task 7 — Make Tenant-Owned Storage Methods Require orgId
--------------------------------------------------------

Problem:

Some storage methods still accept optional orgId:

    getProvider(id, orgId?)
    getPipeline(id, orgId?)
    getJobRun(id, orgId?)
    getSyncRun(id, orgId?)

Optional orgId is risky because future routes can accidentally call these methods without orgId and bypass tenant isolation.

Required implementation:

For tenant-owned resources, prefer required orgId in public storage methods.

Recommended approach:

Create safe public methods:

    getProviderForOrg(id: string, orgId: string)
    getPipelineForOrg(id: string, orgId: string)
    getJobRunForOrg(id: string, orgId: string)
    getSyncRunForOrg(id: string, orgId: string)
    getJobTemplateForOrg(id: string, orgId: string)
    getCredentialForOrg(id: string, orgId: string)
    getCmdbAccountForOrg(id: string, orgId: string)

If an unsafe lookup is needed for internal/background jobs, make it explicit:

    getProviderUnsafeById(id: string)
    getPipelineUnsafeById(id: string)

Add comments:

    // Unsafe: only use in internal jobs after ownership has already been verified.

Better option:

Change existing method signatures so orgId is required and fix all TypeScript call sites.

Example:

    getProvider(id: string, orgId: string)

not:

    getProvider(id: string, orgId?: string)

Acceptance criteria:

- Tenant-owned storage methods require orgId by TypeScript signature.
- Any unsafe method is explicitly named Unsafe and documented.
- Route handlers do not call unsafe methods.
- npm run check catches missing orgId at compile time.
- npm run check passes after all call sites are updated.
