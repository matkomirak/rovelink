Task 1 — Fix Auth Test Harness and DB Dependency
------------------------------------------------

Problem:

tests/authz.test.ts now uses supertest, which is good. However, registerRoutes imports server/db.ts, and server/db.ts throws if DATABASE_URL is missing. Even when DATABASE_URL is set to a dummy value, authMiddleware tries to query the database during JWT authentication.

Current authMiddleware behavior:

    const decoded = jwt.verify(token, JWT_SECRET);
    req.userId = decoded.userId;
    const dbUser = await storage.getUser(decoded.userId);
    req.user = dbUser ?? decodedFallbackUser;
    req.orgId = dbUser?.orgId ?? decoded.orgId;
    next();

Because storage.getUser can throw when the database is unavailable, tests with valid JWTs return 401.

Required fix:

Separate JWT validation errors from database lookup errors.

The middleware should:
1. Verify the token.
2. Set fallback user data from JWT claims immediately.
3. Try to load the DB user.
4. If the DB lookup fails in test mode, continue with JWT claims.
5. In production, either fail safely or log the DB lookup error separately.

Recommended implementation:

    async function authMiddleware(req: AuthRequest, res: Response, next: NextFunction) {
      let token: string | undefined;

      const authHeader = req.headers.authorization;
      if (authHeader?.startsWith("Bearer ")) {
        token = authHeader.substring(7);
      } else if (req.cookies?.auth_token) {
        token = req.cookies.auth_token;
      }

      if (!token) {
        return res.status(401).json({ message: "Unauthorized" });
      }

      let decoded: {
        userId: string;
        role?: string;
        username?: string;
        orgId?: string;
      };

      try {
        decoded = jwt.verify(token, JWT_SECRET) as any;
      } catch {
        return res.status(401).json({ message: "Invalid token" });
      }

      req.userId = decoded.userId;
      req.user = decoded.role
        ? {
            id: decoded.userId,
            username: decoded.username ?? "",
            role: decoded.role,
            orgId: decoded.orgId ?? null
          }
        : undefined;
      req.orgId = decoded.orgId ?? undefined;

      try {
        const dbUser = await storage.getUser(decoded.userId);
        if (dbUser) {
          req.user = dbUser;
          req.orgId = dbUser.orgId ?? undefined;
        }
      } catch (error) {
        if (process.env.NODE_ENV !== "test") {
          console.error("User lookup failed during auth", error);
        }
      }

      if (!req.user) {
        return res.status(401).json({ message: "Unauthorized" });
      }

      next();
    }

Also update package scripts so tests run with NODE_ENV=test:

    "test": "NODE_ENV=test tsx --test tests/*.test.ts",
    "test:authz": "NODE_ENV=test tsx --test tests/authz.test.ts"

If cross-platform Windows compatibility is needed, use cross-env:

    "test": "cross-env NODE_ENV=test tsx --test tests/*.test.ts"

Acceptance criteria:

- npm test does not fail because DATABASE_URL is missing.
- Auth tests do not require a real database connection.
- Valid synthetic JWTs with role/orgId claims are accepted in tests.
- Invalid JWTs still return 401.
- Unauthenticated requests still return 401.
- Viewer requests to admin/operator endpoints return 403, not 401.
- npm test passes.


Task 2 — Make server/db.ts Test-Friendly
----------------------------------------

Problem:

server/db.ts throws immediately if DATABASE_URL is not set. This prevents route/auth tests from importing registerRoutes without a real database.

Current behavior:

    if (!process.env.DATABASE_URL) {
      throw new Error("DATABASE_URL must be set...");
    }

Required fix:

Avoid hard failure during unit/integration tests that do not need a real DB.

Option A — provide a test database URL in the test command:

    "test": "cross-env NODE_ENV=test DATABASE_URL=postgres://test:test@localhost:5432/test tsx --test tests/*.test.ts"

This is not enough by itself if the code tries to connect.

Option B — isolate DB-dependent routes or mock storage in tests.

Option C — refactor createApp/registerRoutes to accept dependencies.

Recommended approach:

Refactor registerRoutes to accept optional dependencies:

    export interface RouteDeps {
      storage?: typeof storage;
      db?: typeof db;
    }

    export async function registerRoutes(app: Express, deps: RouteDeps = {}): Promise<Server> {
      const routeStorage = deps.storage ?? storage;
      const routeDb = deps.db ?? db;
      ...
    }

Then authz tests can pass a mock storage object:

    const mockStorage = {
      getUser: async (id: string) => undefined,
      ...
    };

    server = await registerRoutes(app, { storage: mockStorage as any });

Acceptance criteria:

- Tests can run without a live PostgreSQL database.
- Auth/role tests use mocked storage where DB data is not the thing under test.
- Database health tests are separate and can be skipped unless DATABASE_URL points to a real database.

Task 4 — Finish Tenant Isolation in Pipeline Mapping Routes
-----------------------------------------------------------

Unsafe examples:

    const mappings = await storage.getPipelineMappings(req.params.pipelineId);

    const mapping = await storage.getPipelineMapping(req.params.mapId);

Better storage-layer improvement:

Add tenant-aware mapping methods that join through pipeline:

    getPipelineMapping(mapId: string, pipelineId: string, orgId: string)
    updatePipelineMapping(mapId: string, pipelineId: string, orgId: string, data)
    deletePipelineMapping(mapId: string, pipelineId: string, orgId: string)

Acceptance criteria:

- A user cannot list mappings for another organization's pipeline.
- A user cannot create a mapping under another organization's pipeline.
- A user cannot edit/delete/test another organization's mapping.
- Mapping test cannot access another organization's CMDB adapter.

Task 8 — Use resolveSafePlaybookPath Before Local Ansible Execution
-------------------------------------------------------------------

Problem:

server/services/runner-dispatcher.ts still only validates the playbook string:

    validatePlaybookPathSyntax(template.playbook);

Then it executes the raw path:

    playbookPath: template.playbook,
    inventoryPath: "inventory/netbox.yml"

This is still not safe enough.

Required fix:

Use resolveSafePlaybookPath with the project checkout path.

Implementation outline:

1. Load the template with org scoping.
2. Load the project with org scoping.
3. Resolve the playbook path against project.checkoutPath.
4. Generate or locate a controlled inventory file for the run.
5. Pass only safe resolved paths to LocalRunner.

Example:

    const project = await storage.getProject(template.projectId, run.orgId);
    if (!project) {
      throw new Error("Project not found");
    }

    const safePlaybookPath = await resolveSafePlaybookPath(
      project.checkoutPath,
      template.playbook
    );

    const safeInventoryPath = await createInventoryForRun({
      orgId: run.orgId,
      runId: run.id,
      templateId: template.id
    });

    const result = await runner.execute({
      playbookPath: safePlaybookPath,
      inventoryPath: safeInventoryPath,
      limitExpr: run.limitExpr ?? undefined,
      extraVars: template.extraVars ?? {},
      checkMode: template.checkMode ?? false,
      diffMode: template.diffMode ?? false
    }, onLog);

Do not pass raw template.playbook directly to LocalRunner.

Do not hardcode:

    inventory/netbox.yml

Use a controlled runtime path:

    runtime/inventories/<orgId>/<runId>/inventory.yml

Acceptance criteria:

- Raw template.playbook is never passed directly to LocalRunner.
- Absolute playbook paths are rejected.
- ../ traversal is rejected.
- Symlink escapes are rejected.
- Missing playbooks are rejected.
- Only .yml/.yaml playbooks inside project.checkoutPath are allowed.
- Inventory path is generated by the server, not accepted from the client.
- Add tests for resolveSafePlaybookPath, not only validatePlaybookPathSyntax.
