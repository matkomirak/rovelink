Task 1 — Make npm test Pass Without a Real Database
---------------------------------------------------

Problem:

npm test still imports server/db.ts, and server/db.ts still throws when DATABASE_URL is missing:

    if (!process.env.DATABASE_URL) {
      throw new Error("DATABASE_URL must be set. Did you forget to provision a database?");
    }

This means tests cannot run in a clean CI/Replit environment unless a real database is provisioned first.

Required fix:

Choose one of the following approaches.

Preferred approach: dependency injection / test storage.

Refactor registerRoutes so tests can pass mock dependencies and avoid importing or using the real db for auth/authorization tests.

Example target design:

    export interface RouteDeps {
      storage?: typeof storage;
      db?: typeof db;
    }

    export async function registerRoutes(app: Express, deps: RouteDeps = {}): Promise<Server> {
      const routeStorage = deps.storage ?? storage;
      const routeDb = deps.db ?? db;
      ...
    }

Then tests can use:

    const mockStorage = createMockStorage();
    server = await registerRoutes(app, { storage: mockStorage as any });

Alternative approach:

Create a separate test setup that starts a disposable PostgreSQL database and sets DATABASE_URL before tests run.

Acceptance criteria:

- Running npm test in a clean environment does not immediately fail because DATABASE_URL is missing.
- Authz tests do not require a live database.
- Security/path tests do not require a live database.
- DB integration tests are either isolated behind their own command or start a test DB automatically.


Task 2 — Fix Tenant-Isolation Test Strategy
-------------------------------------------

Problem:

tests/tenant-isolation.test.ts uses the real db:

    import { db } from "../server/db";
    import { organizations } from "../shared/schema";

and tries to insert test organizations in a before hook.

This causes tests to fail unless a real, reachable database exists.

Required fix:

Choose one:

Option A — Make tenant-isolation tests true integration tests.

Create a separate script:

    "test:integration": "NODE_ENV=test tsx --test tests/tenant-isolation.test.ts"

Document that this command requires DATABASE_URL and a test database.

Do not include these integration tests in the default npm test unless the test DB is automatically available.

Default test command should run DB-free tests:

    "test": "NODE_ENV=test tsx --test tests/authz.test.ts tests/security.test.ts tests/playbook-paths.test.ts"

Option B — Mock tenant isolation tests.

Use mocked storage and test route behavior without a real database.

Option C — Provide an automatic test DB.

Use Docker Compose or a test container approach so npm test starts with a real PostgreSQL database.

Acceptance criteria:

- npm test passes in a clean environment.
- Tenant isolation tests are still available.
- If tenant isolation tests require a DB, they run under a separate documented command.
- Test documentation clearly explains which tests are unit/API tests and which are DB integration tests.

Task 4 — Wire resolveSafePlaybookPath Into Local Ansible Execution
------------------------------------------------------------------

Problem:

runner-dispatcher.ts still does not use resolveSafePlaybookPath.

Current behavior:

    let resolvedPlaybookPath: string = template.playbook;
    validatePlaybookPathSyntax(template.playbook);

    const result = await runner.execute({
      playbookPath: resolvedPlaybookPath,
      inventoryPath,
      ...
    });

This only validates the string syntax. It does not verify that the playbook exists inside a checked-out project directory, and it does not protect against symlink escapes.

Required fix:

Implement real project checkoutPath support or fail closed when checkoutPath is missing.

Recommended production-safe behavior:

    if (!template.projectId) {
      throw new Error("Local execution requires a project");
    }

    const project = await storage.getProject(template.projectId, run.orgId);
    if (!project?.checkoutPath) {
      throw new Error("Local execution requires a real project checkoutPath");
    }

    const resolvedPlaybookPath = await resolveSafePlaybookPath(
      project.checkoutPath,
      template.playbook
    );

    const inventoryPath = await createInventoryForRun({
      orgId: run.orgId,
      runId: run.id,
      templateId: template.id
    });

    await runner.execute({
      playbookPath: resolvedPlaybookPath,
      inventoryPath,
      ...
    });

If demo mode must remain, make it explicit and do not allow production local execution without checkoutPath.

Acceptance criteria:

- LocalRunner never receives raw template.playbook in production.
- resolveSafePlaybookPath is used before local execution.
- Missing project checkoutPath fails safely.
- Symlink escape tests are added.
- Inventory path is generated in a controlled runtime directory.


Task 5 — Implement Real Project Sync or Keep It Demo-Only Everywhere
--------------------------------------------------------------------

Problem:

Project sync still uses hardcoded demo playbooks:

    const demoPlaybooks = ["site.yml", "deploy.yml", "rollback.yml"];

The API response labels this as demo, which is good, but the product is not production-ready for local Ansible workflows until real Git checkout exists.

Required fix option A — implement real Git sync:

- Add checkoutPath to project model/schema if not already present.
- Store checkouts under:

    runtime/projects/<orgId>/<projectId>/

- Clone or pull repository using spawn argument arrays.
- Discover .yml/.yaml playbooks from the checkout.
- Store or return discovered playbooks.
- Use credential store for private repositories.
- Never log tokens or credentials.
- Use checkoutPath with resolveSafePlaybookPath during execution.

Required fix option B — keep demo mode:

- Make UI clearly show "Demo Sync".
- Documentation must say repository sync is simulated.
- Local execution should be disabled in production unless a real checkoutPath exists.

Acceptance criteria:
- Either real Git sync works safely, or demo limitations are visible everywhere.
- No production documentation implies real repository sync if it is not implemented.

Task 7 — Enforce or Clarify Settings / AWX Scope
------------------------------------------------

PRODUCTION-HARDENING.md says this is intentionally global and should only be editable by platform admins in a future update.

Current product role model appears to have viewer/operator/admin, but no clear platform-admin distinction.

Required fix:

Choose one model.

Option A — org-scoped settings:

- Add orgId to settings.
- Read/write settings by orgId.
- AWX config is per organization.

Option B — global platform settings:

- Add platformAdmin/superAdmin role.
- Only platform admins can change global AWX settings.
- Organization admins cannot modify global settings.
- Hide settings UI from non-platform admins.

Acceptance criteria:
- AWX token cannot be overwritten by a regular organization admin from another tenant.
- Settings scope is documented and enforced in code.
- Tests cover settings authorization.
